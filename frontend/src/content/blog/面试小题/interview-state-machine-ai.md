## 一、AI 写的代码，常错在哪

### 用 AI 写一个约课小程序时碰到的 8 个错

下面 8 条都是真实碰到过的：代码由 AI 写，靠并发测试、代码审查、自己试用和线上反馈发现。被问到「AI 写错过什么」「你怎么把关」，按这个顺序讲：AI 怎么写的 → 后果 → 怎么发现 → 怎么改 → 规则里从此多了哪一条。

| # | AI 一开始怎么写的 | 后果 | 怎么发现 | 怎么改 |
|---|---|---|---|---|
| 1 | 改余额「先读出来、内存里算、写回绝对值」 | 两个请求读到同一个旧值、写同一个新值，一次扣减凭空消失。8 个并发约课只扣了 1 节；3 节余额被约出去 8 次；8 次并发取消只退回 1 节 | 并发测试 | 判断写进 WHERE：`SET available = available - 1 WHERE user_id = ? AND available >= 1`，看影响行数 |
| 2 | 取消预约的 UPDATE 只判「这条预约有效」，没判「状态是已预约」 | 学员扫码签到和教练点取消同时到，两个都成功：那节课既算上过了，又退回一节课时 | 代码审查提出，并发测试复现 | WHERE 里两个条件都要有 |
| 3 | 教练离职前「先查名下有没有预约，再改状态」，下单那边也是普通查询 | 两边同时通过，留下一条挂在离职教练名下、谁也处理不了的预约，课时永远卡在「占用中」 | 代码审查 | 离职和下单都先锁住教练那一行；所有路径加锁顺序固定为「先用户表、再别的表」，避免互相等待（死锁） |
| 4 | 并发测试吞掉了线程里的异常，而且只断言两个字段中的一个 | 被测方法每次都静默失败，测试照样是绿的。这叫「假绿」：显示通过，其实什么都没测到 | 代码审查 | 异常收集起来重新抛出；每个被并发修改的字段都要断言 |
| 5 | 学员没填昵称时，通知里填掩码手机号 `139****0002`；测试断言的是「填进去的是不是掩码」 | 微信这一格只收汉字、字母、符号，不收数字，整条通知被拒（错误码 47003），没填昵称的学员约课，教练都收不到通知 | 线上：教练反映收不到，查日志找到 47003 | 改成「未填昵称」；测试改成按微信的规则断言「不含数字」，并确认新测试在修之前是红的 |
| 6 | 默认配置是本地开发模式，靠部署脚本里的一行切到生产 | 那一行一旦丢了，模拟登录就生效：带个自定义请求头就能冒充任何人，包括管理员 | 全量代码审查 | 默认改成生产模式，缺密钥直接启动失败 |
| 7 | 扫码签到由后端自己挑课：「先找私教课，找不到再找团课」 | 学员 17:30 的私教没来、教练还没处理，他 18:40 来上团课扫码，签掉的是那节没上的私教课 | 自己用手机试用时发现 | 扫码后列出此刻能签的所有课，由人点一下确认，后端不再猜 |
| 8 | 小程序切换日期时，不检查返回的数据是哪一次请求的 | 先发的请求后返回，A 日的数据显示在 B 日的标题下；教练照着点签到，签的是 A 日那节课 | 代码审查 | 每次请求带编号，回来时编号对不上就丢掉 |

这 8 条背后是 4 个道理：

1. **单线程测试全过不代表对**，改钱、改状态的代码必须有并发测试。
2. **测试本身也要审**：吞异常、只断言一半、拿被测代码自己的输出当预期，都会假绿。
3. **业务规则 AI 猜不出来**：「签哪节课」「学员没来扣不扣课时」只能人定。
4. **出错时默认拒绝**：配置丢了应该起不来，而不是放开。

### 怎么让 AI 少出错

1. **先写规则再写代码**：项目根目录的 `CLAUDE.md` 是 Claude Code 每次开工都会读的规则文件（Codex 读的是 `AGENTS.md`）。里面写业务红线（比如「课时是钱，改余额必须有事务、有流水、有测试」）、技术栈版本、允许用的依赖、编码规范。
2. **先设计后编码**：设计文档 → 实施计划 → 编码 → 测试。大改动先让 AI 出方案，人看过再动手。
3. **关键路径必须有测试，并且反向验证**：「反向验证」就是故意把防线摘掉（比如删掉 WHERE 里的条件），确认测试会变红。不红，说明这条测试没测到东西。
4. **人做验收**：真机用一遍，再先给一小部分用户用（灰度）。
5. **同一个坑不踩第二次**：每次出问题，把结论写回规则文件。例如姓名显示出过一次 `null`，之后规定所有显示姓名的地方都走同一个工具方法；47003 之后规定测试的预期值必须来自外部规则。
6. **把重复劳动写成工具**：比如每接入一个新合作方都要改同样几个文件、查库拿下一个编号，就写成一个 Skill（写给 AI 的操作说明，触发后按步骤执行），哪几步让人确认、哪几步自动做都写清楚。

### 审 AI 代码时看什么

| 看什么 | AI 常见的错 | 怎么查 |
|---|---|---|
| 状态 | 不校验原状态就改；用「不能是某状态」的黑名单，漏掉新加的状态 | 每个改状态的 UPDATE，WHERE 里有没有原状态；允许的转换是不是白名单 |
| 并发 | 先查再改；读出来算完写回 | 找所有「查 → if → 改」的地方，问「两个请求同时进来会怎样」 |
| 幂等 | 回调、消息、用户连点没有去重 | 同一个请求来两次，数据会不会变两次 |
| 事务 | 事务里调第三方接口；该在一个事务里的两步拆开了；同一个类里方法互调导致 `@Transactional` 不生效 | 看事务边界画在哪；外部调用放在事务外 |
| 钱和时间 | 金额用浮点数；时间依赖服务器默认时区（容器默认是 UTC，比北京慢 8 小时） | 金额用「分」存整数；时区显式写死 `Asia/Shanghai` 或存时间戳 |
| 权限和数据 | 后端返回全量、靠前端隐藏；接口只校验登录，不校验「是不是你的单」 | 抓包能看到什么；换个人的 ID 调一次 |
| 测试 | 假绿；拿被测代码的输出当预期；只测正常路径 | 反向验证；预期值来自需求或外部规则 |
| 多实例 | 定时任务每台机器各跑一遍（部署 5 台，提醒就发 5 遍） | 加定时任务先问「部署几台」 |

### 常见问题

#### 你怎么判断 AI 写的代码对不对？

**结论**：不靠通读每一行，靠「规则在前、测试兜底、关键代码人看」。

1. 写之前：规则文件里写清业务红线，AI 照着写，偏离了一眼能看出来。
2. 写的时候：让它先出方案，先审方案里的状态、表、并发防线，方案对了代码才不会大错。
3. 写完：改钱、改状态、对外回调这几类代码逐行看（对照上面的清单）；页面样式这类看效果就行。
4. 测试：关键路径要有并发测试，并且反向验证。
5. 上线：真机验收，灰度，再看线上日志。

#### AI 写的测试能信吗？

不能直接信。常见的三种假绿：吞掉异常；只断言一半字段；拿被测代码自己算出来的值当预期——代码错了，预期跟着错，测试永远绿。

办法：① 预期值来自需求或外部规则（比如微信规定这一格不能有数字），不来自被测代码；② 修 bug 前先写一条能复现它的测试，确认它是红的；③ 反向验证，把防线摘掉看测试会不会红。

#### AI 写代码最容易错在哪？

三类：① **并发和状态**，它默认按「一个人一次点一下」写，不会主动想两个请求同时到；② **业务规则**，它不知道的就猜，猜得还很像那么回事；③ **测试**，它写的测试倾向于证明自己写的代码是对的。

#### 对话很长以后，AI 开始忘规则、乱改，怎么办？

① 规则写进规则文件，不靠聊天里说一遍；② 一个任务一个会话，做完提交，下一件事开新会话；③ 长任务先让它把实施计划写到文件里，按计划一步步做，中途断了能接上；④ 让它只改需要改的文件，改完看 diff（改动对比）再提交。

## 二、找错题：AI 写的代码，挑毛病

面试可能直接给一段代码让你审。下面 4 段是按 AI 常见写法编的，先自己找，至少找到 3 个再往下看答案。前两段是 TypeScript（Node.js 上常用的语言，带类型的 JavaScript）。

### 找错 1：支付成功回调（TypeScript）

```ts
@Post('callback/pay')
async payCallback(@Body() body: PayNotify) {
  const order = await this.orderRepo.findOneBy({ orderNo: body.outTradeNo });
  if (order.status === 'CREATED') {
    order.status = 'PAID';
    order.paidAmount = body.amount;
    await this.orderRepo.save(order);
    await this.dispatchService.assignRider(order);   // 调派单服务
  }
  return { code: 'SUCCESS' };
}
```

**问题在哪**：

1. **没验签**：任何人都能伪造一条「支付成功」。微信支付文档要求商户必须验证通知的签名，并核对通知里的金额和自己订单的金额一致。
2. **没核对金额**：`paidAmount = body.amount` 直接信了对方的数。
3. **先查再改**：两条重复通知同时到，都读到 `CREATED`，都会改、都会派单。改成 `UPDATE ... SET status='PAID' WHERE order_no=? AND status='CREATED'`，影响 1 行才继续。
4. **`save(order)` 写回整行**：会把读出来的旧值盖回其他字段（比如管理员刚把某人设成离职，那人同时改了头像，后写的那次把离职状态盖了回去）。只更新要改的列。
5. **订单不存在时直接报错**：`order` 是空就抛异常、返回 500，对方会一直重发。应该记日志、告警，再决定回成功还是失败。
6. **派单放在回调里同步做**：派单失败或超时 → 回调返回失败 → 对方重发 → 这时状态已经是 `PAID`，就不会再派单了，订单卡住。改成「改状态 + 写一条待派单消息」放同一个事务，提交后异步派单。

**追问**：回调一直不来怎么办？→ 定时任务查「下单超过 N 分钟还是待支付」的订单，主动调支付平台的查单接口。微信支付文档也要求收不到通知时主动查单。

### 找错 2：用户取消订单并退款（Java）

```java
@Transactional
public void cancel(String orderNo) {
    Order order = orderMapper.selectByOrderNo(orderNo);
    if (order.getStatus() == OrderStatus.DELIVERED) {
        throw new BizException("已送达不能取消");
    }
    order.setStatus(OrderStatus.CANCELLED);
    orderMapper.updateById(order);
    payClient.refund(orderNo, order.getAmount());   // HTTP 调支付平台退款
    couponService.giveCoupon(order.getUserId());    // 补偿一张券
}
```

**问题在哪**：

1. **黑名单**：只拦了「已送达」，那「飞行中」也能取消？货在天上怎么办？应该写白名单：只有待支付、待取件能取消。
2. **先查再改 + `updateById` 写整行**：同找错 1。
3. **事务里调第三方退款**：网络调用期间一直占着数据库连接和行锁；退款成功了，后面发券抛异常，数据库回滚成「没取消」，钱却已经退了。
4. **退款没有幂等号**：调用超时后重试，可能退两次。退款要先生成一个退款单号，对方按单号去重。
5. **改法**：事务里只做「条件 UPDATE 改状态 + 插一条退款单（状态：退款中）」；提交后异步调退款接口，带退款单号；结果靠退款回调和主动查询更新；券放到退款成功后再发。

### 找错 3：算一批订单的结算金额（JavaScript）

```js
async function settle(orders) {
  let total = 0;
  orders.forEach(async (o) => {
    const fee = await getFee(o.id);
    total += o.price * 0.8 - fee;
  });
  return total.toFixed(2);
}
```

**问题在哪**：

1. **`forEach` 不会等 `async` 回调**：函数立刻返回 `"0.00"`，后面算出来的都丢了。改成 `for (const o of orders) { await ... }`，或者 `Promise.all` 并发后再加总。
2. **金额用浮点数**：JavaScript 里 `0.1 + 0.2` 不等于 `0.3`。金额一律用「分」存整数，乘比例后按约定的规则取整。
3. **`Promise.all` 一次全发**：订单很多时会同时打出几千个请求，要限制并发数。

### 找错 4：AI 写的并发测试（Java）

```java
@Test
void concurrentBookOnlyOneSucceeds() throws Exception {
    ExecutorService pool = Executors.newFixedThreadPool(8);
    for (int i = 0; i < 8; i++) {
        pool.submit(() -> {
            try { bookingService.book(slot); } catch (Exception ignored) { }
        });
    }
    pool.shutdown();
    pool.awaitTermination(5, TimeUnit.SECONDS);
    assertTrue(bookingMapper.countBySlot(slot) <= 1);
}
```

**问题在哪**：

1. **吞掉异常 + 断言写成 `<= 1`**：如果 `book` 因为配置错了每次都失败，结果是 0 条，测试照样绿。应该断言「恰好成功 1 个」，并把非预期的异常收集起来重新抛出。
2. **只断言预约表**：约课还会扣余额，余额也要断言（剩下的课时 = 原来 − 1）。每个被并发修改的字段都要断言。
3. **8 个线程不一定真的同时开始**：用 `CountDownLatch` 让它们在同一时刻放行，并跑多轮，提高撞上的概率。
4. **最后做反向验证**：把唯一索引或 WHERE 条件摘掉跑一遍，测试必须变红。实际摘掉两条唯一索引重跑，8 个人全约上了同一个格子。

## 三、后端基本功

### 表结构与索引

#### 设计一张配送订单表：字段、类型、索引

```sql
CREATE TABLE t_delivery_order (
  id            BIGINT       NOT NULL,            -- 雪花算法生成，有序
  order_no      VARCHAR(32)  NOT NULL,            -- 业务单号，对外只给它
  user_id       BIGINT       NOT NULL,
  status        VARCHAR(20)  NOT NULL,            -- 状态，见下文状态机
  amount_fen    BIGINT       NOT NULL,            -- 金额，单位分
  from_pad_id   BIGINT       NULL,                -- 起飞的起降场
  to_pad_id     BIGINT       NULL,                -- 降落的起降场
  version       INT          NOT NULL DEFAULT 0,
  create_time   DATETIME(3)  NOT NULL,
  update_time   DATETIME(3)  NOT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_order_no (order_no),
  KEY idx_user_time (user_id, create_time),       -- 「我的订单」按时间倒序
  KEY idx_status_update (status, update_time)     -- 扫「卡在某状态太久」的单
);
```

- **金额用「分」存整数**，不用浮点数。
- **业务单号单独一列并建唯一索引**，不把自增 id 暴露出去（别人能顺着猜出你一天多少单）。
- **每个索引对应一个真实查询**：先列出会怎么查，再建索引。
- **状态变化另记一张流水表**：`t_order_status_log(order_no, from_status, to_status, event, event_id, operator, create_time)`，`event_id` 建唯一索引防同一事件记两次。

**追问**：时间用 DATETIME 还是时间戳？→ 都行，关键是时区要确定。容器默认 UTC、业务是北京时间，「当天不能约当天」这种逻辑差 8 小时就是事故。存秒级时间戳最不容易出错；业务日期（哪一天上课）用 DATE。

#### 唯一索引怎么当最后一道防线？要「释放」的数据怎么建唯一索引？

**结论**：代码里的先行校验负责给出好懂的提示，**正确性由唯一索引保证**，两个都要有。并发时两个请求都能通过先行校验，只有唯一索引挡得住。

**难点**：数据会「失效」（预约取消了、订单作废了），失效后同一个格子要能再约。MySQL 的唯一索引不能只管「有效的行」。

**做法**：加一列 `active_flag`，有效时是 1，失效时改成这一行自己的 id。唯一索引建在 `(coach_id, book_date, time_slot, active_flag)` 上：有效的预约同一格只能有一条；失效的各自 `active_flag` 都不一样，互不冲突，格子就释放了。

反面例子：逻辑删除（只把 `is_delete` 改成 1，不真删）的表直接建唯一索引，删掉再新增同样的数据会撞上那条已删的行。

#### 联合索引的列怎么排？

等值查询的列放前面、范围查询的列放后面，最左边的列必须用上。失效场景见[《MySQL 索引相关》](/blog/mysql-index/)。

#### 主键用自增还是雪花？业务单号怎么生成？

单库用自增最简单；要分库或者多处生成，用雪花算法（时间戳 + 机器号 + 序号拼成 64 位整数，大体按时间递增）。不用随机 UUID 做主键：它无序，插入时会在索引里到处插页，写入变慢。业务标识可以用「前缀 + 雪花」，比如 `bk_1234…`，看前缀就知道是哪类数据。

### 事务与并发

#### 两个请求同时扣同一个余额，会出什么问题？怎么解决？

**问题**：都读到 10，都算出 9，都写回 9，少扣一次，这叫「丢失更新」。不是多台机器才有，同一个 Tomcat 的两个线程就能撞上。

**解决**：判断和修改合成一条 SQL：`UPDATE account SET available = available - 1 WHERE user_id = ? AND available >= 1`，看影响行数，0 行就是余额不够。MySQL 改一行时会给这行加锁，第二个请求要等第一个提交，再拿最新值判断，所以多台机器也不用分布式锁。

#### 条件 UPDATE、乐观锁、SELECT … FOR UPDATE、分布式锁，各什么时候用？

| 办法 | 适合 | 注意 |
|---|---|---|
| 条件 UPDATE | 判断能写进同一行的 WHERE：扣余额、改状态 | 首选，最简单 |
| 乐观锁（version 列） | 要在代码里算很多东西再写回整行 | `WHERE id=? AND version=?`，失败了要重试或报错 |
| `SELECT … FOR UPDATE`（行锁） | 规则跨两张表，判断写不进一个 WHERE | 所有路径加锁顺序一致，否则会死锁；锁住后要用锁里读到的数据判断 |
| 分布式锁（Redis 等） | 要保护的不是数据库里的一行：调第三方、生成文件、跨库 | 锁过期、主从切换丢锁 |

一个实用的规矩：同一行内部的并发一律用条件 UPDATE；只有跨表的规则（比如「在职教练账上不能有课时」）才显式加行锁，并且所有路径的加锁顺序固定。

#### 事务里能调第三方接口吗？

**不要**。① 网络调用可能几秒甚至超时，这期间一直占着数据库连接和行锁，别的请求排队，连接池被占满；② 对方成功了、我们后面回滚了，两边就对不上，数据库回滚撤不回已经发出去的请求。

**做法**：事务里只改自己的数据，并写一条「待发送」记录（本地消息表：和业务数据同一个库、同一个事务写入，提交后由后台任务读出来发送，失败就重试）。对方接口要支持按我们的单号去重。

#### @Transactional 什么时候不生效？

同一个类里方法互相调用（不经过代理）；方法不是 public；异常在方法里被 catch 掉了；抛的是受检异常（默认只对 RuntimeException 和 Error 回滚，要配 `rollbackFor`）；在新开的线程里执行（事务绑定在当前线程上）；类没有交给 Spring 管理。隔离级别和 MVCC 见[《MySQL 数据库事务相关》](/blog/mysql-transactions/)。

#### 什么情况会死锁？怎么避免？

两个事务各锁住一行，又都去等对方那一行。避免：所有代码路径按同一个顺序加锁；事务尽量短；一次锁多行时按主键排好序。出了死锁，MySQL 会选一个事务回滚，`SHOW ENGINE INNODB STATUS` 能看到最近一次死锁的两条 SQL。行锁、间隙锁见[《MySQL 锁相关》](/blog/mysql-locks/)。

### 幂等与防重

**幂等**：同一个请求做一次和做多次，结果一样。**防重**：防止同一件事被做两次（重复下单、重复扣款、重复派单）。重复的来源有四个：用户连点、网络超时后重试、第三方重复通知、消息队列重复投递。

#### 用户连点两次「下单」，怎么防止下两单？

1. **前端**：点了按钮立刻置灰，请求回来再恢复。只能挡手快，挡不住网络重试。
2. **请求号**：进入下单页时后端先发一个请求号（或前端生成），下单时带上；后端把请求号存进订单表并建唯一索引，第二次插入撞索引，直接返回第一次的结果。
3. **业务唯一性**：业务上本来就唯一的东西（同一个用户同一个时段只能约一节课），直接建唯一索引。

#### 第三方回调、消息队列重复投递，怎么保证只处理一次？

两道防线：① **事件去重**：对方的通知号或消息号存一张表、建唯一索引，插入失败说明处理过；② **状态条件**：改状态的 UPDATE 带原状态，重复来的第二次影响 0 行，直接回复成功。完整流程见场景题 2。

微信支付的文档也是这么要求的：同一条通知可能发多次，商户必须能正确处理重复通知；先查业务数据的状态，已经处理过就直接返回结果；并用锁控制并发，避免同时进来的两条把数据弄坏。

#### 调对方接口超时了，要不要重试？

超时不等于失败，对方可能已经成功了。所以：① 先用同一个单号去**查**对方的结果，查到成功就按成功处理；② 查不到或查到失败，再用**同一个单号**重试，对方按单号去重；③ 一直不确定的，标「处理中」，由定时任务继续查，超过次数转人工。

#### 幂等号谁来生成？存多久？

谁发起谁生成：调对方时用我们的业务单号；对方调我们时用对方的通知号。存在业务表里就和数据一样久；单独的去重表可以按对方最长的重发时间来清理（比如对方最多重发一天，就留一周）。

### 线上数据问题

#### 用户说「订单状态不对」，你怎么查？

1. **问清楚**：哪一单、几点、在哪个页面点了什么、看到了什么。
2. **看数据**：订单当前状态 + 状态流水，最后一次是哪个事件改的、谁改的。
3. **看日志**：按时间找到那次请求，拿它的 traceId（一次请求从头到尾共用的编号）把整条链路的日志捞全，看请求有没有到、被哪条规则拒了、有没有报错。
4. **对第三方**：回调有没有来、来了几次、我们回了什么；必要时调对方查询接口。
5. **修**：先修这一单的数据（走后台操作、留记录，不直接改库），再修根因，最后加监控，别让同类问题等用户来报。

两个容易踩的坑：日志里只搜错误码可能搜不到（那一行被拆开或格式不同），换中文关键词或按 traceId 搜；成功的操作不打日志，就分不清「成功了」和「根本没走到」。

#### 怎么在用户发现之前发现数据问题？

- **对账**：两份应该一致的数据定期比。比如余额分「可用、占用、已消耗」三段时，三段之和必须等于流水累计；「是不是会员」的标记和会员余额表必须对得上。可以直接写成一条测试或定时任务。
- **卡单告警**：定时扫「在某个状态停留超过 N 分钟」的订单（订单表上 `(status, update_time)` 那个索引就是为它建的）。
- **关键操作留痕**：改钱、改状态的地方，成功也要打日志。

**落到代码上就一条规矩**：每次改状态都是 `UPDATE … SET status = 新状态 WHERE order_no = ? AND status = 原状态`，影响 1 行才做后续的事（写流水、通知下游），影响 0 行说明状态已经变了。

三种改状态的写法，差别只在并发和乱序时才看得出来：

| 写法 | 一条条操作 | 两条支付回调同时到 | 送达后用户再点取消 |
|---|---|---|---|
| A. 条件 UPDATE：原状态写进 WHERE | 正常；重复回调影响 0 行 | 只有一条成功 | 影响 0 行，拒绝 |
| B. 先查再改：代码里 if 判断，UPDATE 不带原状态 | 正常 | **两条都先读到「待支付」，判断都通过：记两笔收入、派两次骑手** | if 拦下 |
| C. 不判断原状态，直接改 | 重复回调会再记一笔收入 | 两条都成功 | **改成已取消并退款：货送到了，钱也退了** |

B 最容易骗过人：单线程测试全过，只有并发时才出错。

### 把一个需求拆成状态机、接口、表

拿到一个需求（比如「做无人机配送下单」），按这个顺序拆，边说边写：

1. **先问边界**：谁会改订单状态（用户、骑手端、无人机、起降场、客服）？哪些步骤是异步回来的？哪一步之后不能取消？出了异常谁处理？
2. **列状态和事件**：画上面那样的图，每条箭头写清楚是哪个事件、谁触发的。
3. **拆数据**：一单分三段，每段有自己的执行方和进度，所以除了订单表，再加一张**分段任务表** `t_delivery_leg(order_no, seq, leg_type, carrier_id, status, ...)`：第 1 段骑手、第 2 段无人机、第 3 段骑手（或机器人）。订单状态由分段的进度推着走。
4. **定接口**：用户端（下单、取消、查进度），骑手端（接单、取件、送达），设备和第三方回调（支付结果、起飞、降落、异常），后台（人工处理异常单）。每个会被重复调的接口写清楚靠什么去重。
5. **列风险**：重复事件、乱序事件、丢事件（卡单）、并发（取消和起飞同时到）、钱（退款幂等）。逐条写出办法，拿去评审。

### 对不合理的需求提意见

**先弄清楚需求背后真正要解决的问题，再给替代方案和代价**，不是简单说「做不了」。约课小程序里的几个例子：

- **网页管理后台不做**：做网页要自己做登录、买域名、走 ICP 备案（两三周），会把云托管「免备案」的好处整个抵消掉。管理功能改成放进同一个小程序、按身份显示。
- **灰度不按百分比放量**：一个拳馆就这些人，按百分比会让一半学员能用、一半不能，纯制造混乱。改成「先只告诉一部分学员」。
- **「导航到这里」不做**：用这一页的人已经站在商场里了，缺的不是「怎么到商场」，而是「进了商场怎么找到门」，那是两张指引海报在回答的事。
- **「学员没来扣课时」去掉**：最初的设计里有，和拳馆核对后按他们的规矩改成没来不扣、全额退回。涉及用户和钱的规则，先确认再动。

### 常见问题

#### 为什么状态转换要用白名单，不用黑名单？

黑名单是「这几个状态不能做」，白名单是「只有这几个状态能做」。业务会加新状态（比如后来加了「备降中」），黑名单不会自动拦它，新状态默认就能取消、能签收；白名单默认拒绝，漏了最多是功能不能用，不会把数据改错。

#### 无人机上报的事件乱序了（「降落」比「起飞」先到），怎么办？

1. 状态机先挡：订单还在「待起飞」，「降落」不是合法事件，条件 UPDATE 影响 0 行。
2. 但不能直接扔：把事件原文存下来（事件表，带设备时间和序号），标「待处理」。等「起飞」到了，再按设备上的时间顺序把后面的事件补着推进。
3. 如果「起飞」一直没来（丢了），用设备当前的实际状态校正：主动查设备，或者以最新一次上报的位置为准，并告警给人看。
4. 事件要带设备侧的序号或时间，后台只接受比当前更新的。

#### 状态变化要不要记流水？记什么？

要。记：订单号、原状态、新状态、事件、事件号（唯一索引）、谁触发的、什么时候。用处：查问题时知道是哪一步、谁改的；对账时能逐条重放；客服能给用户看进度。和改状态写在同一个事务里，改成功才记。

#### 状态很多、转换很复杂时，代码怎么组织？

把允许的转换写成一张表（枚举或配置）：`(原状态, 事件) → 新状态`，所有改状态都走同一个方法，由它查表、拼条件 UPDATE、写流水、发事件。不要在各个业务方法里散着写 `if (status == ...)`，那样加一个状态要改十几处。Java 里可以用 Spring Statemachine 这类库，但多数业务一张转换表就够。

## 五、Node.js、小程序和设备后端

### Node.js 和 NestJS（对照 Spring）

**Node.js** 是让 JavaScript 跑在服务器上的运行环境。**NestJS** 是 Node.js 上的后端框架，写法很像 Spring：模块、依赖注入、用装饰器（类似 Java 注解）声明路由。

| Spring 里的 | NestJS 里对应的 |
|---|---|
| `@RestController` + `@GetMapping` | `@Controller('orders')` + `@Get()` |
| `@Service`，构造器注入 | `@Injectable()` 的 Provider，构造器注入 |
| `@Configuration` / Spring Boot 的模块划分 | `@Module({ controllers, providers, imports })` |
| Filter / HandlerInterceptor | Middleware（中间件） |
| Spring Security 的权限判断 | Guard（守卫，决定这个请求能不能进） |
| AOP 环绕通知 | Interceptor（拦截器，请求前后都能加逻辑） |
| `@Valid` 参数校验、类型转换 | Pipe（管道） |
| `@ControllerAdvice` 全局异常处理 | Exception Filter（异常过滤器） |
| MyBatis Plus / JPA | TypeORM、Prisma（把表映射成对象的工具） |
| `@Transactional` | TypeORM 的 `dataSource.transaction(async (manager) => { ... })`，或手动用 `QueryRunner` 开启、提交、回滚 |

**一个请求在 NestJS 里经过的顺序**（官方文档）：中间件 → 守卫 → 拦截器（前半段）→ 管道 → 控制器方法 → Service → 拦截器（后半段）→ 异常过滤器（出了没被捕获的异常才走）→ 返回。

```ts
@Controller('orders')
export class OrdersController {
  constructor(private readonly orders: OrdersService) {}   // 构造器注入，和 Spring 一样

  @Post(':orderNo/cancel')
  @UseGuards(AuthGuard)                                     // 先过守卫：登录了才能进
  cancel(@Param('orderNo') orderNo: string) {
    return this.orders.cancel(orderNo);
  }
}
```

**和 Java 最大的不同：单线程 + 事件循环**。Java 的 Tomcat 是一个请求占一个线程，线程在等数据库时就干等着。Node.js 用一个主线程跑所有 JavaScript 代码，遇到数据库、网络这种要等的操作，交出去后先处理别的请求，结果回来了再接着执行回调。这个「不停地取下一件准备好的事来做」的循环就叫**事件循环**。所以：

- 等 IO 多、计算少的业务（大部分接口）一个线程能扛很多并发；
- **某个请求里做了很重的同步计算，所有请求都得等它**，连健康检查都会超时。重计算要放到 `worker_threads`（Node 的工作线程）或者单独的服务里；
- **并发问题照样有**：两个请求在 `await` 之间会交替执行，「先查再改」照样出错；数据库层面的问题和 Java 完全一样，条件 UPDATE、唯一索引这些办法原样适用。

#### Java 背景转 Node.js，难点在哪？

框架层面不难：NestJS 的模块、依赖注入、守卫、拦截器基本是 Spring 那一套思路。要适应的是语言细节和生态（异步写法、包管理、ORM 的用法）。而判断代码对不对的那部分——状态机有没有漏、并发下会不会扣两次钱、回调重复了怎么办——和语言无关。

#### NestJS 里怎么写事务？

用 TypeORM 的话：`this.dataSource.transaction(async (manager) => { ... })`，回调里所有数据库操作都要用这个 `manager`，回调正常结束就提交、抛异常就回滚。也可以手动用 `QueryRunner`：`connect → startTransaction → commitTransaction / rollbackTransaction → release`，NestJS 文档推荐这种，控制更细。和 Spring 的区别：没有 `@Transactional` 那种「自动把当前线程里的操作都包进事务」，要显式把事务对象传下去，忘了用 `manager` 的那句就不在事务里。

#### React 的 `useEffect` 里发请求要注意什么？

最常见的坑是请求乱序：用户快速切换筛选条件，先发的请求后返回，把新数据盖掉。办法：给每次请求编号，回来时只认最新的那个，或者在 `useEffect` 的清理函数里把上一次请求作废。另外依赖写漏了会拿到旧值，写多了会反复请求。

### 微信小程序

- **标准登录流程**：小程序里调 `wx.login` 拿到一个一次性的 `code` → 传给自己的后端 → 后端拿 `code` 加上小程序的密钥调微信接口，换回这个用户在本小程序里的唯一编号 `openid` → 后端发自己的登录凭证给小程序。
- **另一种做法：微信云托管**。小程序通过 `wx.cloud.callContainer` 走微信内部通道调后端，微信把 `X-WX-OPENID` 等请求头直接注入进来，后端不用自己做登录；但必须校验 `X-WX-SOURCE`，确认请求真的来自微信。不经过公网域名，所以不用做 ICP 备案。
- **手机号不存明文**：存四列，可解密的密文、MD5（用来等值查询）、掩码（对外只给它）、后四位（用来按尾号搜）。返回真号的接口全系统只留一个，且只给管理员。

#### 小程序是公开的，接口怎么防止别人抓包看到不该看的数据？

内部数据在后端就不返回，不靠前端隐藏。比如排期分两个接口：没登录的访客只能看「营业时间表」（时段和在职教练，没有任何预约数据）；登录用户看「可约情况」，但不带约课人姓名，只有教练和管理员能看到是谁约的。如果一个接口返回全量、前端按身份藏，抓包就全看见了。后端也只信微信注入或微信接口换来的 `openid`，不信前端自己传上来的用户编号。

### 支付分账、对账清结算

- **分账**：一笔收款按规则分给多方。比如用户付 30 元，平台留多少、两个骑手各拿多少、起降场运营方拿多少。一般用支付平台的分账功能：先收进平台的商户号，订单完成后按规则发起分账，钱再到各方账户。
- **清分**：把每一方应得多少算清楚；**结算**：把钱实际打过去。通常每天（或按周）跑一次。
- **对账**：拿我们的记录和支付平台的记录逐笔比。支付平台每天会出一份对账单，下载下来和自己的订单、退款记录按单号对：我们有对方没有、对方有我们没有、金额不一致，三类差异逐条处理。

#### 分账怎么设计？订单退款了怎么办？

1. 订单完成后才分账，不在支付那一刻分（还可能退款）。
2. 分账单独一张表：每一方一行，`(order_no, receiver, amount_fen, status)`，分账请求带唯一的分账单号，对方按单号去重。
3. 所有分出去的钱加起来必须等于可分的总额，金额用分，取整的零头规定归平台。
4. 分账后退款，要先发起「分账回退」把钱从各方收回来，再退给用户。规则要在业务上先定好：已经结算给骑手的钱还收不收回。

#### 对账发现「对方显示支付成功，我们订单还是待支付」，怎么处理？

说明回调丢了，主动查询也没补上。处理：按对账单那一条，走正常的「支付成功」流程推进状态（同一个条件 UPDATE，幂等）；如果订单已经超时关闭了，就走自动退款。然后查为什么回调和主动查询都没兜住，补监控。

### 无人机、机器人、智能设备的后端

**设备和服务器怎么通信：MQTT**。物联网里最常用的消息协议，设备和服务器都连到一个中转服务（Broker），按「主题」收发消息：无人机往 `drone/123/status` 发位置和电量，服务器订阅这个主题；服务器往 `drone/123/cmd` 发指令，无人机订阅它。不用 HTTP 的原因：设备网络不稳、要省电省流量，而且服务器要能主动推指令给设备。

- **QoS（送达级别）**：0 是最多一次，可能丢；1 是至少一次，保证到但可能重复；2 是恰好一次。用 QoS 1 时，**收到的消息可能重复，处理要幂等**，和支付回调一样。
- **遗嘱消息**：设备连上时预先登记一条消息，如果它不是正常断开（比如没电、掉线），中转服务替它发出去。服务器订阅它，就能及时知道设备掉线。
- **保留消息**：标成保留的消息，新订阅者一连上就能收到，适合「设备当前状态」这种只关心最新值的数据。

**端侧 AI**：模型直接跑在设备上（无人机识别降落点、机器狗避障），不用每次传回云端，因为来不及、也可能没信号。后端配合的是下发模型版本、收集设备回传的数据和识别结果。

#### 服务器怎么给无人机下发指令（比如「起飞」），怎么确认它执行了？

1. 先在库里建指令记录：`(command_id, drone_id, type, status=已下发, sent_time)`，`command_id` 唯一。
2. 发 MQTT 消息，带 `command_id`。设备按 `command_id` 去重，同一条指令收到两次只执行一次。
3. 设备执行后回一条「已执行」（带 `command_id`），服务器条件 UPDATE 指令状态。
4. 超时没回：先查设备当前状态（是不是其实已经起飞了），再决定重发同一个 `command_id` 还是告警。和「调对方接口超时」是同一个道理。
5. **以设备实际上报的状态为准**，不以「我们发过指令」为准。后台记两个值：期望状态（我们要它做什么）和实际状态（它报上来的），两者长时间不一致就告警。

#### 怎么判断设备在线还是离线？

三层：① 设备定时发心跳（比如每 10 秒），服务器记最后一次时间，超过几个周期没收到算离线；② MQTT 的遗嘱消息，异常断开时中转服务替设备发「我掉线了」；③ 业务上：飞行中的无人机掉线是严重事件，立刻告警给人，订单转「异常」。在线状态放 Redis 这种快的地方，别每次心跳都写数据库。

#### 设备每秒上报位置，数据量很大，怎么存？

- 最新位置放 Redis，给地图实时显示用。
- 历史轨迹按时间写入适合时间序列的存储（时序数据库，或者按天分表），用于回放、查问题。
- 上报先进消息队列削峰，再批量写入，不要一条一条写数据库。
- 老数据降采样（比如一个月前的只留每分钟一个点）或转到便宜的存储。

#### 起降场管理平台做成 SaaS，要注意什么？

**SaaS**：软件做成在线服务，多个客户（叫「租户」，比如不同城市、不同运营方的起降场）共用一套系统，数据互相隔离。要点：

- 每张业务表带 `tenant_id`，所有查询都必须带上它。靠人记一定会漏，要在框架层统一加（MyBatis Plus 有多租户插件，Node 里在 ORM 层或中间件统一处理）。
- 大客户要求更强隔离时，可以单独一个库。
- 权限分两层：租户之间，和租户内部的角色。
- 配置按租户可调（营业时间、可用设备、收费规则），不要写死。

#### 机器狗、机器人送最后一段，和骑手送有什么不同？

对后端来说它是另一种「运力」（能干活的资源：骑手、无人机、机器人），接口形态和无人机类似（指令、上报、心跳）。不同在于：速度慢、单次能送的距离短，要考虑电量和充电排队；路线上有门禁、电梯、人流，失败率更高，所以「送不到」的分支（转人工骑手）一定要设计好。分段任务表里把第 3 段的执行方从「骑手」换成「机器人」，状态机不用改。

无人机飞行的总规定是《无人驾驶航空器飞行管理暂行条例》，2024 年 1 月 1 日起施行；航线、空域另有专门的审批流程。

### 数据看板

#### 看板数据从哪来？能直接查业务库吗？

不能直接查主库：看板的统计查询又大又慢，会拖慢下单这些核心接口。办法：① 查从库（只读的复制库）；② 定时把统计结果算好存进汇总表，看板只读汇总表；③ 数据量大了再上专门的分析库。每个指标的口径（「准时」怎么算、取消单算不算）要写成文档，和产品、运营对齐，不然各说各的数。

#### 低空配送的看板应该看哪些指标？

单量和架次；每段平均耗时（地面取件、等待起飞、飞行、末端派送），找出哪段最慢；准时率；取消率和取消原因；异常单数（返航、备降、掉线）；每架无人机、每个起降场的利用率；单均成本。核心是**看分段耗时找瓶颈**。

## 六、场景设计题

### 题 1 设计「骑手 + 无人机 + 骑手」的配送订单系统

**题目**：用户下单，骑手取件送到起降场，无人机飞到另一个起降场，再由骑手送到收件人。设计状态、表、接口，说清楚怎么保证不出错。

**先问**：日单量多少？哪些步骤可以取消？天气不能飞时怎么办（改地面配送还是等）？无人机由谁调度（自己还是合作方）？

**参考答案**

1. **状态**：画上面的状态机图；主线 8 个状态，加取消和异常两条支线。说出「白名单，表外的转换一律拒绝」。
2. **表**：订单表；分段任务表（三段，各自有执行方和状态）；状态流水表（事件号唯一）；设备事件原文表（存所有上报，带设备序号）；支付单、退款单。
3. **接口**：用户端、骑手端、设备回调、支付回调、后台异常处理。每个会被重复调的接口都有去重依据。
4. **改状态**：统一一个方法，条件 UPDATE + 写流水 + 发事件（本地消息表），同一个事务。
5. **派运力**：支付成功后异步派骑手；骑手送到起降场 A 时派无人机；无人机起飞后预派骑手 B。派单方法见题 3。
6. **异常**：天气、返航、备降 → 订单转「异常」，人工处理：重新派无人机、改地面配送、或取消退款，每种都要有接口和操作记录。
7. **卡单**：定时扫「某状态停留过久」的订单，按状态告警（取件中 30 分钟、飞行中超过航线预计时间的两倍……阈值和产品定）。

**追问**：用户在骑手 A 已经取件后取消呢？→ 业务规则问题，先问产品：能取消就要「骑手把货送回」这一支线，并且收取消费；不能取消就只能拒绝。不要自己拍板。

### 题 2 第三方回调（支付结果、设备上报）怎么保证处理正确

**参考答案**

1. **验签**：先核对签名，确认是对方发的、内容没被改；支付通知还要核对金额和我们订单一致（微信支付文档的要求）。验签不过直接拒绝。
2. **先存原文**：原始报文落库（通知号唯一），方便查问题和补处理。
3. **去重**：通知号唯一索引 + 状态条件 UPDATE，两道防线。
4. **快速应答**：只做「验签、存原文、改状态」这几步就回成功，耗时的后续（派单、发通知）放到异步。按微信支付文档，返回 200 或 204 表示成功，返回 4XX 或 5XX 表示失败，失败或超时它会按一定间隔重发。
5. **兜底**：回调可能一直不来。定时任务查「下单超过 N 分钟仍待支付」的订单，主动调查单接口。
6. **对账**：每天拿对方的对账单逐笔比，抓前面几道都漏掉的。

### 题 3 派运力：同一架无人机不能同时被派两单

**参考答案**

1. **占用用条件 UPDATE**：`UPDATE t_drone SET status='ASSIGNED', task_id=? WHERE drone_id=? AND status='IDLE' AND battery >= ?`，影响 1 行才算派上；0 行换下一架。同一个事务里再把无人机号写进分段任务（`WHERE leg_id=? AND drone_id IS NULL`，防止同一段被派两架）。
2. **唯一索引兜底**：分段任务表上建「一架无人机同时只能有一个进行中的任务」的唯一索引。MySQL 不能只对部分行建唯一索引，用前面讲的 `active_flag` 办法：进行中是 1，结束后改成自己的 id。
3. **不需要分布式锁**：数据库改一行时会锁这一行，多台机器天然排队。抢单特别激烈（同一时刻上百单抢几架飞机）才考虑把空闲无人机放到 Redis 队列里分配。
4. **选哪架**：起降场 A 有哪些空闲的、电量够不够飞这条航线、载重够不够。第一版按简单规则，跑出数据再优化，规则由产品定。
5. **释放**：任务结束、取消、异常都要把无人机放回空闲，同样用条件 UPDATE；再加一个定时对账，「无人机是占用状态，但它的任务已经结束」的情况要能发现。

约课里「一个教练的一个时段只能被一个学员约」是同一道题：先行校验给提示，唯一索引保证正确。把这两条唯一索引摘掉重跑并发测试，8 个人全约上了同一个格子。

### 题 4 现场用 AI 编程工具做一个小功能，你怎么做

面试官看的是过程，**边做边把判断说出来**。

1. **先问清需求**：列出不清楚的点问面试官（就像题 1 的「先问」），不要直接让 AI 开写。
2. **让 AI 读项目**：读规则文件和相关代码，弄清楚现有的写法。
3. **让它先出方案**：状态、表、接口、要写哪些测试。审方案，指出遗漏（比如「这里两个请求同时到会怎样」）。
4. **先写关键测试**：尤其是并发、重复请求的测试，跑一下确认是红的。
5. **再写实现**，跑测试变绿。
6. **反向验证**：把防线摘掉，测试要变红。
7. **自己读关键代码**：改状态、改钱的部分逐行看，对照第一节的审查清单。
8. **自测**：造几条数据从接口调一遍；写简短的接口说明；提交说明写清改了什么、为什么。

### 题 5 用户投诉：东西已经收到了，App 上还显示「待派送」

**参考答案**

1. **查流水**：最后一次状态变化是「降落」，后面没有「骑手取货」「签收」。
2. **查日志**：骑手 B 端有没有发过「取货」请求？如果发过却被拒，看拒绝原因；如果签收请求到了，会因为状态不是「派送中」被状态机拒掉，签收就一起丢了。
3. **可能的根因**：骑手端网络不好，「取货」请求失败没重试；或者骑手直接点了「送达」跳过了「取货」。
4. **修这一单**：后台按「取货 → 签收」补状态，记操作人和原因，不直接改数据库。
5. **修根因**：骑手端失败要重试；和产品讨论「签收」是否允许从「待派送」直接到，如果允许就加进转换表（白名单显式加），而不是放松校验。
6. **加监控**：「待派送」超过 N 分钟告警，别等用户投诉。

**这题在考**：状态机严格带来的代价（合法的事件丢了，后面的都进不来），以及修数据的规矩。
